# Phase 6 build plan: open demo course and the Teacher module

Two pieces of work, built in this order:

- **Part A.** Replace the synthetic DEMO101 course with a real, openly licensed course
  built from Microsoft's MIT-licensed *AI for Beginners* and *ML for Beginners*.
- **Part B.** Add a Teacher module to LEA. Behind a teacher/admin login, a teacher can
  load course content, review and edit the knowledge-component (KC) model, get an audit
  of their content, see which concepts real students struggle with, and try the course
  as a student.

Background and evidence: `docs/teacher/RESEARCH.md` (the research report). Rules for
working in this repo: see the README. Design system: `docs/design/DESIGN.md` (Chalkboard).

## Principles

1. **API first.** Every teacher action is a service and an API endpoint with tests
   before any screen uses it.
2. **Research data stays clean.** LEA's data is used in published papers. Every recorded
   event carries a session kind (`real`, `test` or `simulated`). Teacher previews are
   `test` and never reach research logs, analytics or exports.
3. **Learner data never attaches to the wrong concept.** Granular-objective (GO) IDs are
   immutable once a KC model is published. Edits create a new version, and splits,
   merges and retirements are recorded in a lineage map.
4. **The teacher decides.** Audits and analytics produce ranked, explained findings that
   the teacher accepts or dismisses, never scores or automatic changes. LLM judgements
   are labelled as suggestions, with the evidence tier shown (see Part B, Audit).
5. **Privacy by default.** Aggregates only; suppress any statistic drawn from fewer than
   5 students; chat excerpts are pseudonymised and shown only above that threshold; no
   per-student view in the first release.
6. **Nothing changes for students.** Unless a milestone says so, the adaptive loop,
   grading and mastery behave exactly as now. Anything that changes them is marked
   **(research)** in `CHANGELOG.md` and needs the researcher's approval first.

## Before starting

- Phase 4 (Flutter app) and Phase 5 (private courses) should be merged to `main`.
  Work on a new branch, `phase-6-teacher`.
- **Exception: milestone B1 (the event log) is urgent.** The Redis evidence list keeps
  only each student's last 50 graded answers per course, so real students' history is
  lost until B1 ships. If students will use LEA before Phase 6 starts, do B1 first as
  its own small branch.

## Part A: Replace DEMO101 with an open course

### A1. Source and licence

- Sources:
  - <https://github.com/microsoft/AI-For-Beginners> (MIT licence), lessons 01–05, and
    lesson 18 or 20 only if week 6 is included.
  - <https://github.com/microsoft/ML-For-Beginners> (MIT licence): the introductory
    lessons and the quiz bank in `quiz-app/`.
- Before committing anything, re-read both repos' `LICENSE` files and record the date
  and commit hash used. English text only (skip `translations/`).
- **Leave out images** (the sketchnotes and other PNGs). It is unclear whether the MIT
  licence covers them, and RAG uses the text anyway.
- Ship with the course: a copy of each MIT licence, and `ATTRIBUTION.md` listing the
  source repos, commit hashes, which files were used and what was changed.

### A2. The course

- **Code `AIML101`**, name "Introduction to AI and Machine Learning (open course)". Use a
  new code rather than reusing DEMO101: the new GO IDs would otherwise collide with
  existing students' DEMO101 mastery.
- Proposed weeks (confirm with the researcher after reading the lessons):

| Week | Topic | Source |
|---|---|---|
| 1 | Introduction and history of AI | AI4B lesson 01 |
| 2 | Symbolic AI: knowledge representation and expert systems | AI4B lesson 02 |
| 3 | Machine learning basics | ML4B intro lessons (and regression, if needed) |
| 4 | Neural networks: the perceptron | AI4B lesson 03 |
| 5 | Multi-layer networks, frameworks and overfitting | AI4B lessons 04–05 |
| 6 (optional) | Ethics or transformers/LLMs | AI4B lesson 18 or 20 |

- Build it with the existing onboarding pipeline (`data_foundation/`, see
  `docs/COURSE_CREATION.md`): ingestion into ChromaDB, KC generation, a course profile
  (`allows_code: true`, Python), and RAG verification with `verify_rag_content.py`.
  Report the OpenAI cost before running anything expensive.
- **Quizzes.** Inspect the `quiz-app/` format (and any quizzes in AI for Beginners).
  Import the questions for the chosen lessons as a reference question bank, tagged to
  GOs, in a documented format. For now these seed the content audit (B6) and the
  quiz-generation prompt. Using them directly in Quiz mode would change grading and item
  selection, so it is **(research)** and needs approval.
- Record in `ATTRIBUTION.md` which KC-model fields were generated by LEA.

### A3. Switch over

- `AIML101` becomes the default course at registration and in docs.
- Keep DEMO101 for the tests only. Move it to `tests/fixtures/data/DEMO101` and point the
  test data copy at it, so the 150+ existing tests keep their known structure. The published
  papers' code is in the first public repository (tag `v1.0-snsc`).
- Update `README.md`, `docs/SETUP.md`, `docs/COURSE_CREATION.md` and the Streamlit/Flutter
  default course. Leave the design screenshots as they are (they illustrate the layout).
- Tests: a smoke test that `AIML101` loads, has 5–6 weeks, every GO has retrievable
  content, and the course profile is valid.

**Done when:** a new student can register for AIML101 and use Chat, Tutor and Quiz on
real content; licences and attribution are in place; all tests pass.

## Part B: The Teacher module

### Roles and access

| Role | Can |
|---|---|
| `student` | Everything LEA does today |
| `teacher` | Everything a student can, plus the Teacher area for the courses they own |
| `admin` | Everything, plus create teacher accounts, assign course ownership and see all courses |

- The first admin is created with `scripts/manage_account.py` (add `make-admin` and
  `make-teacher` commands). There is no self-service teacher sign-up.
- Ownership: a Redis set `course:{code}:owners`. Every `/teach/...` endpoint checks the
  caller owns the course, or is an admin.
- An audit trail of admin and teacher actions (who, what, when, course) in the event log
  (B1).

### B1. Durable event log (urgent; no behaviour change)

- **Storage: SQLite** (`data/lea_events.db`, gitignored, WAL mode, stdlib `sqlite3`), not
  Redis. The Redis Cloud free tier is too small to hold history, and SQLite is durable
  and queryable on the host PC. One writer at a time behind a lock; a documented backup
  (copy the file).
- One `events` table: `id, ts, course, kc_version, username_hash, session_kind (real |
  test | simulated), mode (quiz | tutor | chat), type, go_id, lo_id, week, correct,
  score, question_type, payload_json`. The raw username is pseudonymised with a salted
  hash; keep the salt in `.env`.
- Written from the services:
  - graded and ungraded answers (from `record_graded_response`);
  - quiz start, end and each answer's chosen option;
  - tutor start, end and reply outcomes (including consecutive-incorrect and YouTube
    help triggers);
  - chat questions: text stored pseudonymised, for later topic analysis;
  - scaffolding and motivation decisions (the same fields as the CSV logs);
  - teacher and admin actions (these store the actor's real username, not a hash: they
    are an audit trail of staff actions).
- `session_kind` comes from the account (see B7): test and preview accounts write
  `test`. The existing CSV research logs and any research export skip `test`.
- Consent: add `research_consent` (true, false or unset) to the user record, and
  capture it at registration with plain wording the researcher approves. Research exports
  include only consented learners. Teacher analytics for teaching improvement use all
  `real` sessions in aggregate. Confirm this split with the researcher and their ethics
  approval before release.
- Tests: every student-facing action writes the expected event; test sessions are
  excluded from exports; the database survives a restart.

### B2. Roles, ownership, admin endpoints

- The `role` field on the user record (default `student`), returned in `/me`.
- `/admin/users`: list, create a teacher, set a role or activate/deactivate (revoking
  tokens). `/admin/courses/{code}/owners`: add or remove owners.
- Dependencies `require_teacher(course)` and `require_admin`. 403 otherwise.
- Tests: students get 403 on every `/teach` and `/admin` route; a teacher can't reach
  another teacher's course.

### B3. Course onboarding as background jobs

- Create a course: code, name, discipline, `allows_code`, code language, number of
  weeks.
- Upload materials (PDF, DOCX, PPTX, XLSX, MD, MP3/MP4/WAV), one or many files,
  optionally assigned to a week. Limits: 50 MB per file, 1 GB per course; checks on type
  and name. Stored under `data/course_uploads/<CODE>/` (gitignored). Private course
  content must never be committed; extend the `data/` allowlist rules if needed.
- Jobs run in-process like the consolidation worker (a thread started by
  `start_background_work()` reading a Redis job list). No Celery or RQ. A job hash
  `job:{id}` holds status, step, percent, log lines and a cost estimate. Steps: convert
  → transcribe → chunk and embed → generate draft KC model → course profile → verify
  retrieval.
- Show an estimated OpenAI cost before a run; the teacher confirms. One active job per
  course; jobs can be cancelled.
- Endpoints: `/teach/courses` (list, create), `/teach/courses/{code}/uploads`
  (list, add, delete), `/teach/courses/{code}/jobs` (start, list),
  `/teach/jobs/{id}` (status, cancel).

### B4. KC model versions and review

- Versions on disk: `data/kc_models/<CODE>/versions/v{n}.json`, with a `published`
  pointer. The running system reads the published version only. Students keep using it
  while a draft is edited.
- **ID rules:** only the API assigns IDs. Existing GO IDs never change or get reused.
  New objectives get new IDs, and removed ones are marked `retired`, not deleted. A
  `lineage` section records splits (`old → [new…]`), merges (`[old…] → new`) and
  retirements.
- Editing:
  - **In-app table:** week → LO → GO rows with name, description, Bloom level,
    mastery threshold, keywords, prerequisites; add, remove, reorder, split and merge.
  - **Spreadsheet round-trip:** export to XLSX with an ID column and a read-me sheet;
    import it back. The import is validated (IDs unchanged or blank for new rows, no
    duplicates, thresholds 0.5–0.95, prerequisites exist and have no cycles, every week
    has objectives) and becomes a draft with a line-by-line diff. Nothing is applied
    silently.
- Each generated objective shows its source excerpt (the retrieved chunk) so the teacher
  can check it.
- Publishing: shows the diff and the effect on existing students (how many have mastery
  on retired or split GOs). On publish, mastery follows the lineage: splits copy the
  mastery to each new GO, merges take the mean, and retired GOs are kept but ignored.
  The KC cache is invalidated.
- Record in the event log how many objectives the teacher edited, added or removed and
  how long the review took. This is research data for a gap identified in RESEARCH.md.
- Endpoints: `/teach/courses/{code}/kc` (versions), `/kc/draft` (get, replace rows),
  `/kc/draft/validate`, `/kc/draft/export` (XLSX), `/kc/draft/import`, `/kc/diff`,
  `/kc/publish`.

### B5. Content audit

Run on demand against a KC version. Findings are listed by severity with an
explanation, the evidence, a link to the objective or file, the **evidence tier**, and
accept/dismiss with a note. Findings and decisions are stored for comparison between
runs.

| Check | How | Tier |
|---|---|---|
| Accessibility: missing alt text, low colour contrast in slides, heading structure, captions for audio/video | Parse PPTX/DOCX/PDF; WCAG-style rules | Well supported |
| Question-writing flaws in the question bank (negative wording, "all of the above", clues in the stem, implausible distractors) | Rules first, then LLM, in the style of SAQUET | Well supported |
| Bloom-level balance per week (share of remember, understand, apply…) | LLM classification, shown as a distribution, not per item | Moderate |
| Coverage: objectives with little or no supporting material | Retrieval score of each GO's description against the course store, with the threshold calibrated per course | Experimental |
| Redundancy: objectives or chunks that duplicate each other | Embedding similarity | Experimental |
| Prerequisite order: an objective taught before its prerequisite | KC graph against week order | Rule-based (reliable) |
| Alignment: questions without an objective, objectives without questions | Tags and LLM judgement | Experimental |
| Readability and slide density | Readability metrics and words per slide, reported as information, not as pass/fail | Informational |

Optionally, align the report's headings with OSCQR (CC BY 4.0). Don't copy Quality
Matters wording (proprietary).

### B6. Student analytics

Computed from the event log (`session_kind = real` only), for the published KC version,
per course, optionally filtered by week and date range. Any figure drawn from fewer than
5 students is suppressed and shown as "not enough students yet".

1. **Objective overview (lead view).** For each GO: a mastery band (mastered, developing,
   struggling, or **not enough evidence**), number of students, graded attempts,
   first-attempt accuracy, and attempts needed to reach mastery. Sorted by the "needs
   attention" score described in item 5.
2. **Learning curves** per GO and LO: error rate by practice opportunity. A flat or rising
   curve suggests the objective or its teaching needs work, or that the GO should be
   split. Include a DataShop-style CSV export.
3. **Common wrong answers** per quiz question: the distribution of chosen options, and
   the wording of the most common wrong option.
4. **Tutor struggle signals** per GO: share of students with three or more consecutive
   incorrect replies, YouTube help triggered, and ended sessions without advancing.
5. **"Needs attention" ranking**, clearly labelled as LEA's heuristic: low first-attempt
   accuracy + flat learning curve + many tutor struggles + many chat questions on the
   topic. Show which factor drove each ranking.
6. **Chat confusion topics:** chat questions (pseudonymised) clustered by topic with an
   LLM and mapped to GOs, with counts and up to three paraphrased example questions. Only
   topics asked by at least 5 students are shown. Validate the clustering on a sample
   first and report agreement.
7. **Suggested action** for each flagged objective, as a drafted note for the teacher,
   for example "add a worked example", "split into two objectives" or "revisit the slide
   deck `Week3.pptx`, slides 4–7". Optionally, "draft an explainer": the LLM writes a
   short explanation from the course content for the teacher to edit. It is never
   published without approval.

Also show usage (active students, sessions, time on task), but after the concept views,
not first.

### B7. Preview as a student

- "Try as a student" creates or reuses a sandbox student account per teacher and course
  (`<teacher>~preview`), flagged as test. Every event it writes is `test`. It can use
  the published version **or the current draft**.
- The app shows a persistent banner, "Preview: your answers aren't recorded as student
  data", with **Reset preview** and **Back to teaching** buttons.
- An optional **explain panel** (teacher only) on each turn shows the GO the turn mapped
  to, the mastery update, ZPD, cognitive load, motivation state, the chosen scaffolding
  and the retrieved course chunks. Add a teacher-only `debug` field to the API
  responses; students never receive it.
- A checklist of suggested probes per week ("ask something off-topic", "give a wrong
  answer twice", "answer the diagnostic with 'I don't know'").

### B8. Teacher UI (in the Flutter app)

- **Design first:** before coding, produce mockups of the teacher screens in the
  Chalkboard style (same tokens and type as `docs/design/DESIGN.md`). Make them
  screenshots plus a short spec, like `docs/design/`, and **stop for the researcher's
  approval.**
- Screens:
  - Teacher home (courses owned, with status);
  - course setup and uploads with job progress;
  - KC review (table, diff, import and export, publish);
  - audit findings;
  - analytics (overview, objective detail with curves and wrong answers, chat topics);
  - preview mode;
  - admin (users, owners).
- Routes under `/teach` and `/admin`, shown only to teachers and admins (a "Teaching" item
  in the rail or bottom nav). Wide screens first: teachers work at a desk. Phone layout
  can be read-only.
- The Streamlit UI stays student-only. No teacher pages there.

### B9. Documentation and evaluation readiness

- `docs/teacher/GUIDE.md` (for teachers), `docs/API.md` (new endpoints), `CHANGELOG.md`
  Phase 6 section with **(research)** marks, `docs/SETUP.md` (creating the first admin,
  backing up `lea_events.db`).
- Instrumentation for a later study (see RESEARCH.md, "gaps"): KC review edits and time,
  findings accepted and dismissed, flagged objectives and later changes, analytics views
  opened. All go into the event log, tagged as teacher actions.

## Milestones and order

Commit after each; run the backend tests, `flutter analyze` and `flutter test`; stop
for the researcher's review.

1. **B1** Event log (urgent, see above).
2. **A1–A3** AIML101 open course.
3. **B2** Roles, ownership, admin endpoints.
4. **B3** Onboarding jobs and uploads.
5. **B4** KC versions, review, import/export, publish with lineage.
6. **B8 design checkpoint:** teacher screen mockups; wait for approval.
7. **B7** Preview mode (API and UI), then the UI for B3 and B4.
8. **B5** Content audit (API and UI).
9. **B6** Analytics (API and UI).
10. **B9** Docs, changelog, and a full end-to-end run: an admin creates a teacher; the
    teacher creates a course, uploads AIML101's materials, reviews and publishes the KC
    model, runs the audit, previews as a student, and sees analytics from simulated
    students (seeded as `simulated`, never `real`).

## Definition of done

- A teacher can do the end-to-end run above in the Flutter app without touching files
  or scripts.
- Students notice no change; the existing tests pass; new tests cover every endpoint,
  permission, the ID and lineage rules, suppression below 5 students, and the exclusion
  of test sessions from analytics and exports.
- AIML101 replaces DEMO101 everywhere a student sees it, with licences and attribution
  in place.
- No private course content, databases, uploads or secrets are committed.
